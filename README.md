# notunh

The better UNH app, at [notunh.app](https://notunh.app): a PWA built with Vite and [bruh](https://github.com/Technical-Source/bruh), served as static assets from Cloudflare Workers.

Each section is its own page and bundle, sharing a shell (`src/shell/`: the `<head>`, theme, icons, Intl formatting, the one clock and visibility every page follows, remembered state, polling, which keeps a live source's last answer, and when it came, apart from whether asking it is failing, and the service worker):

- `/` (`index.html.tsx`): what's here, who made it, and where the data comes from
- `/map/` (`map/index.html.tsx`, `src/map/`): live Wildcat Transit buses and routes on MapLibre GL with the OpenFreeMap Liberty style, and bus + walking directions
- `/dining/` (`dining/index.html.tsx`, `src/dining/`): dining hall menus, with search by food or ingredient and diet and allergen filters
- `/laundry/` (`laundry/index.html.tsx`, `src/laundry/`): which washers and dryers are free in every laundry room, and when each room is usually busy, with each room at its own address, like `/laundry/adams-tower/`

Within a section, `state.mts` holds the reactive state and live data, `ui/` the components, and the rest the logic, with the pure parts property tested. Each npm package builds into its own chunk, so a change to the app leaves maplibre cached.

### Offline first, updated live

Once built, every page opens from the cache at once, its code and data too, and the service worker (`src/sw/`, built to `/sw.js`) checks the network behind it:

- **A page's `<head>` is its release manifest** (`src/shell/manifest.mts`): when it was built (`<meta name="release">`), and published again, if it was, as a rollback is (`<meta name="published">`), its code, including maplibre's worker, which `vite.config.mts` names there since only the code that starts it knows its name, and a preload link for each bundled JSON file, by name: the map's timetable, model, walking network, gazetteer, tiles week, style, and laundry and dining buildings, the dining index, and the laundry rooms' usual weeks. The build hashes them like code, so a page's HTML says exactly which code and which data it is, and they load alongside the code. Pages read their data through `latest(name, schema)` (`src/shell/build.mts`), a reactive value that everything derived from it follows; a file that doesn't fit its schema, which checks its shape and where it came from but takes big arrays of our own making on trust, is a load that failed like any other, tried again later, each time longer, and past every cache (`cache: "reload"`, which the worker honors too), so a file that once answered as the wrong thing is fetched afresh rather than read back from the cache forever. A load that hangs is given up on after a minute, so it holds up no other.
- **A newer copy of a page** is kept only once everything it names, and everything its data files say they can't work without (the map's style), is confirmed kept, each file being what its name says it is (a sign-in page answering with a 200 at a hashed URL is served but never kept), so it always opens whole offline, then sent to the page's open windows. Keeping a release is strict in this way, and a file that hasn't arrived whole within a minute keeps it out too, its siblings called off with it; answering an ordinary request is not: a put that fails, a full quota, or a cache that won't open never fails a response, and a file kept behind an answer whose body stalls holds up the worker's other writes for a minute at most. If only its data differs, the page loads every changed file, each its own slot swapped in where it is as it loads, keeping the trip, the itinerary chosen, the stop selected, and the map's camera, and tries again, later each time, for any that fails: a page's files join only by stable ids and coordinates, the timetable's stop and route ids, the model's, the gazetteer's and places' positions, the dining index's content-named children, so any build's file goes with any other's, nothing has to be swapped in as a group, and what's derived from several is derived again from whichever are newest. A newer week of tiles is fetched afresh in place of the old, and a newer style comes in as the differences from the one showing. If its code differs, which a running page can't swap, the page reloads the next time it's out of view and not in the middle of a bus ride, or at once if it already is, so no one sees it, and picks up what it keeps between visits, like the trip being planned and the bus being ridden. No prompts. A page asks for its own copy to be checked when it comes back into view and every quarter hour in view, so a window that never navigates still hears of the nightly build; a copy published before the one kept, as from an edge not yet caught up, is left alone, by the worker and by the page alike, so going back to an earlier release means publishing it again (see Deploying). A newer copy announced while a file first loads is loaded right after it.
- **Retention**: what the cache keeps is the closure of every generation still in use, which is each cached page's current and previous copy and whatever the open windows answer that they run, asked over a `MessageChannel` with a second to answer, and nothing else. A data file can ask more of the cache through one shape, `Retain = { required?, files?, folders? }`: the style manifest requires its `style.json`, fetched with the page, the dining index names its files, kept if they're there, and the tiles and style manifests their folders, so the worker knows nothing of any of them. Every write to the cache and every pruning takes its turn on one queue, so nothing is kept while a pruning runs and no page's files are mistaken for another's leftovers. Pruning happens after a newer page is kept, on activation, and when the origin's quota is hit, where failing to keep a file never fails serving it: the worker prunes, then lets go of all the tiles, then all the fonts and sprites, each rung once per storm, which lasts until a put succeeds or a page is next taken in, puts failing together sharing each rung rather than each climbing one. The cache is named anew when what it keeps changes meaning, and activating lets go of every older one: the first worker's pages named only their code, which loaded their data by URL, so what one needs can't be told, and it's fetched afresh like a page not visited yet, while a tab still open on one fetches any file it hadn't loaded from the network, and when one is gone, the worker sends that tab to its page afresh, once, since its code has no way to recover. A window that can't answer, as one frozen or in the back-forward cache, is covered as far back as its page's previous generation; one older than that, once it resumes, hears of the newer build and reloads out of view, or after an hour away reloads at once, and may 404 on a file it hadn't loaded before then.
- **Live data**, Umo's buses and the laundry API, is never cached, and each page polls it as before.

`tests/shell/sw.test.mts` drives the worker against an in-memory world, with the sequences from the 2026-10-18 reviews as named regressions, and `sw.model.test.mts` runs it against a model over generated sequences of releases, windows, going offline, a quota full for every file or only the large ones, the origin answering a sign-in page for a data file, the network holding a page's files while anything else happens, restarts, the worker killed mid-staging, and frozen windows. `npm run test:browser` runs the same release sequences through Chromium and WebKit (`tests/browser/`), apart from `npm test`, including a release whose data shows on the page, one whose worker differs, which takes over an open tab and leaves the first worker's pages to be fetched afresh, and a rollback from release C to A. [docs/storage.md](docs/storage.md) is the policy for every artifact and table: who makes it, its version, where it lives, how long, and how it goes.

Safari deletes a site's caches, service worker, and localStorage after seven days of use without a visit to it, unless it's on the home screen, and pages then come from the network as on a first visit, and are cached again.

The layers, each importing only those before it: `src/shared/` and `src/geo/`, which import nothing of ours; the walking network and the timetable (`src/map/graph.mts`, `feed.mts`, `shapes.mts`) on `geo`; where each bus is along its route and when it got to and left each stop, as distributions (`locate.mts`, the location model), which the map follows live (`tracking.mts`) and the nightly extraction (`events.mts`) reads a day of fixes with; how a bus is expected to move on from there, as one course (`movement.mts`: each bus's pace, and the model's legs, profiles along them, and stops), which is both where the map draws it and when it leaves each stop ahead; and the forecast of them (`forecast.mts`: each followed bus's course along its trip, the timetable shifted by how late each route runs for the rest, and a live source's observations, which `umo.mts` makes of Umo's predictions, saying which runs aren't coming, so nothing past it reads Umo's shape); routing (`walks.mts`, `plan.mts`) on the forecast and the walks; publication and storage (`src/shell/`, `src/sw/`, the Worker, and `scripts/`) on `shared`; and the pages' state and UI on everything. `scripts/` import `src/`, never the other way, and `worker/` imports only `src/shared/`, `src/laundry/`, and the map's pure parts. `src/shared/` is what the pages, the Worker, and the build all use, with neither the DOM nor Node: Durham's clock and calendar (`time.mts`), the fold every learned model shares (`learn.mts`), `getJson`, which checks what it fetches against any Standard Schema it's given, and the slugs links name places by. Every boundary checks what crosses it with a [Valibot](https://valibot.dev) schema, which is also where its type comes from: Umo's, LaundryConnect's, Nutrislice's, and Photon's answers, keeping only the vehicles, predictions, machines, and places that fit, the data files the pages load, the map data release's pointer and manifest, and the bodies the Worker's build routes take, validated by `@hono/standard-validator` against `drizzle-valibot`'s schemas of the tables. `src/geo/` is the one geometry everything measures by, pure and knowing nothing of stops or the map: positions as `[lon, lat]` or `{ lat, lon }`, meters on the WGS84 ellipsoid by cheap-ruler's rulers (`projection.mts`, the only place one is made), lines measured out in meters with points and stretches along them, each with a ruler of its own for what's beside it (`lines.mts`), boxes always as west, south, east, north, indexed by Flatbush for finding what's near, and outlines as rings (`boxes.mts`), and map matching along lines (`follow.mts`), weighed as its caller says a bus or a walker keeps to them. The transit side (`src/map/shapes.mts`, routes' shapes with their stops along them) and the walking network build on it, and so do the scripts. Time comes in two units, and only two:

- **Epoch milliseconds**, as `Date.now()` gives them, for every instant that crosses a boundary: Worker rows, API JSON, page state, and everything in laundry.
- **Schedule seconds** where times are compared with the GTFS timetable, which counts seconds from a service day's start: the planner, the bus model, and the visits it learns from, in the D1 `visits` table too.

A calendar day is a `Day`, `YYYY-MM-DD` in Durham, which sorts and compares as text, and weekdays count from Monday.

## Map

### Data

- **Live**: the Umo IQ rider API (`api.prd-1.iq.live.umoiq.com/v2.0/riders/agencies/unh`), the backend of `rider.umoiq.com` and the Umo apps. No key, open CORS, so browsers poll it directly: vehicles every 5 s, and predictions every 30 s for routes with a bus out.
- **Schedule**: Wildcat Transit's GTFS feed on National RTAP (the one Google Maps uses). The host has no CORS, so `npm run data` converts it into `src/map/gtfs.json` at build time, and CI rebuilds nightly. Umo's trip and stop ids match the GTFS ones, so predictions shift the timetable per trip. The first build to see a new feed version archives it in the Worker (`/api/models/gtfs`, as of that day), so a day's visits are always replayed against the timetable then in force.
- **OpenStreetMap**: Geofabrik's extract of New Hampshire, which the **Map data** workflow (`.github/workflows/map.yml`) downloads each week and `scripts/map/osm.mts` makes into everything the map has of OpenStreetMap: the streets and paths people walk around Durham, as the network in `src/map/walk.json`, the gazetteer in `src/map/gazetteer.json`, every place OSM names, with each one's kind, middle, and extent, and each building's outline and doors, and our own tiles (below). The three are one generation, each marked with where it came from (`src/map/made.mts`: the extract's date, and a hash of the code, campus profile, packages, and Planetiler that made it, which together name the version), published whole as the immutable release `map-data-<version>`, one archive with a manifest of hashes, and then named by `latest.json` on the `map-data` release, so every build gets all of a generation or fails (`scripts/map/release.mts`). It reads the extract itself in about 3 s (`scripts/map/pbf.mts`: the file's framing, blocks, and protobuf are `@osmix/pbf`'s, and what OpenStreetMap's fields mean and how elements are gathered are ours, so a file cut short is refused as truncated rather than misread). While there's no release, the walk and gazetteer are the fixtures' (`tests/fixtures/data/src/map/`), which carry their provenance too; `npm run osm:refresh` takes the latest from the release, and `node scripts/map/osm.mts <extract.osm.pbf> <planetiler.jar> [--release <folder>]` makes them from an extract, the tiles too with Planetiler (and Java 21 or later), and stages the release.
- **Tiles**: made from the same extract with [Planetiler](https://github.com/onthegomap/planetiler) (`scripts/map/tiles.mts`) in two sets (`src/map/tiles.mts`), served from `public/data/map/tiles/<version>/<set>/{z}/{x}/{y}.pbf`: the OpenMapTiles base map Liberty draws, at zooms 10 to 14 around Durham, Dover, and Portsmouth, and a campus set in a schema of our own (`scripts/map/campus.yml`), at zooms 14 to 16 around Durham, with building names, parking lots, doors, benches, emergency phones, drinking water, fences and walls, and trees. Each set is cut to exactly the tiles wholly inside its boxes, which stay in New Hampshire, as the extract has nothing of Maine across the river, with an empty file where Planetiler made none, so every tile the map asks here for is here. The style names tiles as `tiles://<set>/{z}/{x}/{y}`, and the map's `tiles` protocol fetches each from here where the set has it, else from upstream (OpenFreeMap's pinned planet build, for the base map), else none, so a tile is wholly ours or wholly OpenFreeMap's and the two meet without a seam. They're stored uncompressed, as gzip only saves a quarter of them and maplibre can't read it without a `Content-Encoding` header; Cloudflare compresses them on the way if it takes their type to be compressible. About 1,200 files and 3.2 MB a version, and a build keeps the version the site served before beside the new one, so a tab still on last night's map isn't left without, against the free plan's 20,000 files per deploy.
- **Base map**: OpenFreeMap's Liberty style, which `scripts/map/style.mts` makes ours at build time (`src/map/style.mts`) in a folder under `public/data/map/` named by a hash of everything in it, so its style, sprite, and fonts always match, and names in `src/map/style.json`, which the map's page bundles like its other data: its sprite and the Latin and punctuation glyph ranges of its fonts served from our origin (rarer ranges still come from OpenFreeMap), its tiles ours where we have them and else from the planet build current then, so their URLs never change, our campus tiles drawn too, and its layers redrawn where they hide what's in the tiles: house numbers, bicycle parking and ATMs, woods, railways and platforms, campus land use and pitches, without unnamed flowerbeds, barriers, or bus stops our own stops already show. The service worker keeps the style's folder and the tiles' week with the page that names them, and lets them go with it; on the origin, as with the tiles, the folder the site served before stays one more build beside the new one, fetched back from the site, for a map tab still on it.
- **Walking**: along the network (`src/map/graph.mts`, `src/map/walks.mts`), which keeps every part of OpenStreetMap's paths with twenty or more of them, to and from a building's nearest door where the gazetteer knows its doors, else from the place itself, joining the network by the nearest few paths and letting the shortest way decide. Where the network doesn't join a walk's ends, the walk is an estimate, a straight line a quarter longer, which the map draws dashed and faint rather than dotted, and which the planner is told of, allowing an estimate more time than a walk along the network, so a timed transfer by one isn't counted on as closely.
- **Place search and names**: the gazetteer, stops, and laundry and dining buildings first, searched with uFuzzy as the dining page searches foods (`src/map/search.mts`), each name once, as the place by it nearest the middle of campus; Photon only for addresses, or when little is found here. A tapped spot is named by the map's label there, else the gazetteer's building it's in, by its outline where the gazetteer has it, or a place within 60 m, else the tiles' house number, else Photon (`src/map/gazetteer.mts`).
- **Laundry and dining buildings**: `scripts/map/places.mts` matches them to the campus's buildings in the gazetteer, into `src/map/places.json`, which names a hash of the gazetteer, rooms, menus, and code it was derived from, and is derived again when any of them changes. The laundry vendor puts every room at the same spot, so rooms are matched to their residence halls by name, with a small alias table where OSM names a building otherwise; a room or hall left unmatched fails the build. The map shows them quietly and plans to one when it's tapped, and `/map/?to=laundry/<room>` or `?to=dining/<hall>`, as the laundry and dining pages link, plans there from your location.

**Where each bus is** is the location model's (`src/map/locate.mts`): GPS puts a bus within a few meters, but only every 10 to 30 s, so what's uncertain is what it did in between. Each fix is matched to a place along one of its route's shapes, by an HMM over the places it could be, weighed by how far off each is, its heading, and whether driving there from the place before is plausible (Viterbi over a day's fixes, and only what's come so far live). Between two matched fixes, the bus drove as buses do, speeding up to a cruising speed and braking to a stop, stopping or not at each stop on the way and dwelling there, or halted somewhere, for however long the time between the fixes leaves; that's integrated over a grid of cruising speeds and ways of splitting the time, deterministically, which gives each stop's arrival and departure as quantiles, how likely the bus stopped there, and how its time was spent along the way from the stop before. A bus stopped within 20 m of a stop is at it, as 98 % of stopped fixes are; there are no zones, and nothing is timed by crossing one. A particle filter was tried first and measured too noisy (notunh-model-research/2026-10-19_location/).

Buses are drawn where they likely are now, not just where they last reported, along their **course** (`src/map/movement.mts`): from where the location model has the bus, at the speed it's going, settling toward the pace that gets it to the next stop when the model expects, each leg as long as the model expects at this time of day, scaled by how slow or quick that bus has lately been (its pace, a Kalman filter over how much longer than expected each leg took it, drifting back to usual over an hour), its time spent along the leg as buses' is (slower pulling out and in, and wherever the leg holds them up), and at each stop as long as buses spend there, or until its scheduled time where its trip waits for the timetable. The same course is the forecast of when it leaves each stop ahead, so the map never draws a bus somewhere its departures disagree with.

Every departure shown, on a stop's list, a bus's stops, and in trip planning, is the model's (`src/map/forecast.mts`). A bus the map is following is forecast along its course from where the location model has it, on along its trip's stops, and how much longer it stays at a stop it's at from how long it's been there; where its trip ends at the start of a later one of its route's the same service day, on through a layover into the one due to start nearest when it would (or the one Umo has it on next), if that's due no more than half an hour after the bus could start it, or an hour before, for a bus running late; it's what the bus is expected to run, not live until it's seen on it, and the day's last loop goes on into nothing. Of two buses tagged with one trip, the one nearer its time runs it. A route that keeps to its timetable (routes 3 and 4, which mark timepoints) is forecast from the timetable shifted by how late it runs from half an hour ahead, as breaks and holds put it back on it, and every run with no bus followed is its timetable shifted likewise. For a route that runs by headway with no bus followed, a stop's list says how often its buses come and how soon the next likely does, rather than its timetable's times, which say nothing of when they actually will. Umo's predictions still say which buses are on which trips and which runs aren't coming, and set the times of a bus Umo has on a trip the map isn't following, or of any run of a route the model knows nothing of; its schedule's guesses at when a bus will start a run, no better than the model's, don't. Held out a day at a time on Oct 7 to 19, this took the median error of a followed bus's departures from 60, 126 and 202 s to 28, 50 and 75 s at 1, 5 and 10 minutes ahead, and of every departure from 65, 128 and 186 s to 32, 60 and 90 s (`notunh-model-research/2026-10-19_heldout/IMPLEMENTED.md`). Following each bus with the location model rather than zone crossings, its events read the same way and the model trained on them, took 4.7, 3.6 and 2.4 s more off the median at 1, 3 and 5 minutes on 11, 11 and 9 of 11 days, 20 s at 20 minutes, and 16 to 260 s off the mean at every lead, with 10 minutes unchanged (`notunh-model-research/2026-10-19_location/`).

Trip planning is a Connection Scan over the day's runs as forecast, each with how far off its times may be (the chain's spread, scaled to how far off its forecasts have turned out at that lead, or how much its route's lateness varies), and a live source's observations of trips at stops with how far ahead it covers each route at each stop, which is all the planner knows of Umo, with a reverse scan so each option leaves as late as possible. The timetable keeps each stop time's own word on getting on and off ("Arrivals Only" stops) and on getting there before leaving, and the planner never boards, alights, or arrives against it. A trip due at a stop Umo is predicting, between its answer and the furthest it predicts a trip there, less how late the trip may be running, that it doesn't mention is dropped (the campus connectors run by headway, not to the timetable), though a far look ahead at one stop says nothing of another, and predictions older than three polls are dropped too, for the schedule. How early to be at a stop weighs the chance the bus waits there for its scheduled time, as the model has learned it, against how early it might otherwise leave, so a bus that waits half the time gets most of the slack of one that never does. Itineraries are kept across replans only while they would show the same, so a newer timetable's or fresher delays always come through, and the one chosen is remembered by its key.

### The model

Each build fits `src/map/model.json` (`scripts/map/model.mts`), bundled like the timetable. For every completed service day since the last model, it extracts each bus's visits to stops from the Worker's samples (`src/map/events.mts`, through the location model the map follows buses with, each visit naming the extractor that read it), stores them back in D1 as `visits`, sums the day up (`summarize`), stores that too, and folds the day's summary into decayed statistics with a 4-week half-life (`src/map/model.mts`, on the fold in `src/shared/learn.mts`), so a refit, or another half-life, is folding the stored summaries again rather than extracting again: the time of each leg between stops a bus visited one after the other, driven or lost to its GPS on the way (so a request-only stop it passes costs nothing, and a highway stretch it can't be followed along is still learned), by route, weekday or weekend, and two hours of the day; how a leg's time is spent along it; time at each stop, and laying over at the start of a trip, by route; how much longer a bus some while at a stop still stays; whether early buses wait at a stop for their scheduled time; how late each route runs; and how often each route's buses come by the hour. Every estimate leans on a broader one while it has little data (a leg's own mean on how long legs that long take, a time of day's on the leg's), and an empty model has none, so the map falls back on its old constants. Each day is also scored (`scripts/map/replay.mts`): at 1, 3, 5, 10, 20, 30, and 60 minutes before each departure, the runs as the map would have forecast them from what it would have seen of the buses then, its fixes replayed through the same location model in the order they came, against Umo's own prediction and the timetable, which sizes the band the planner leaves slack by from how many of its own standard deviations the model's forecasts turned out off. The model's stored shape has a version (3 since the location model, 2026-10-20): a stored model of another is refit from the first day the Worker still has samples for, as the first build after a change of shape does.

Everything goes through the Worker's token-gated `/api/rows/:name` and `/api/models/:name` (see Deploying), so the build needs only `BUILD_TOKEN`, never D1 credentials, and learning runs only after the typecheck and tests pass. The latest model is the last stored, whatever day it runs through, so a refit of a new shape that runs out of time partway is stored as a checkpoint behind the old shape's model and the next build carries on from it. A model is stored only over the one the build read (a compare-and-swap on the latest's revision, which every write renews, so two builds can't both succeed, and a build that read the old model can't overwrite a checkpoint), so two builds learning at once converge on one, the second bundling the first's, if it's of its shape, rather than overwriting it. Without the token, or the Worker, the last model stays (or an empty one), so the model never fails the build. `npm run model -- --rebuild` refits from every stored visit, extracting again where samples are still kept, each day against the timetable archived for it.

## Dining

Menus come from Nutrislice (`unh.api.nutrislice.com`, behind `unh.nutrislice.com`): a week per hall and meal, with stations, ingredients, diet and allergen tags, and nutrition, published about two weeks ahead. It has no CORS, so `npm run data` fetches today through the end of what's posted, and splits it so the page only loads what it shows:

- `src/dining/menus.json`, the index the page bundles: halls, which meals each hall serves each day, and the name of every other file
- under `public/data/dining/`, each named by a hash of what's in it:
  - a file per hall per day, with each food's name, tags, and calories (about 2 KB gzipped)
  - a file per food, with its ingredients and nutrition, loaded when it's opened; a food served all week is one file, and stays cached across nightly rebuilds
  - every upcoming food with its ingredients and servings, loaded on the first search

The index names every file it uses, by path, and the service worker keeps them with it, dropping the rest once no retained index or open dining tab names them. On the origin, a file stays published while the index the site serves names it, and two nights past the last index that did, for tabs still on an index naming it: each build fetches them back from the site, as a build starts from nothing, and leaves the record of them, with when each goes, at `/data/dining/published.json` for the next (`scripts/dining/publish.mts`). Search, filters, and everything else run in the browser.

## Laundry

The rooms' Speed Queen machines report to LaundryConnect (`laundryconnectlive.com`), which has no CORS, so the page asks the Worker. The room list reads `/api/laundry/rooms`, every room's free washers and dryers as the collector last saw them, made from D1 alone and shared at the edge for 5 minutes, so the list never reaches the vendor; counts made over half an hour ago, as when the collector or the asking has fallen behind, say when they're from. An open room reads `/api/laundry/rooms/:id`, which fetches it live with the asker's own User-Agent and shares the answer for 30 s, falling back to the collector's last record (marked stale) when the vendor can't answer. `npm run data` lists the rooms into `src/laundry/rooms.json`, each with the slug of its address.

Each room has its own address, `/laundry/<room>/`: the Worker answers it with the laundry page (any other `/laundry/…` is a 404), the page moves between rooms with `history.pushState`, the service worker keeps the one laundry page for every room offline, where the page says when there's no such room, and `vite.config.mts` does the same in development.

`src/laundry/infer.mts` decides what to claim about each machine: a running machine's countdown is its own while it keeps reporting, a quiet one past its end is probably done, and a finished one sits done until its door opens.

The Worker's laundry cron polls every room every 5 minutes (15 overnight), a quarter of the rooms each minute between the fifths, and writes status changes to D1 (`transitions`, `latest`, `polls`) plus one current snapshot per room (`room_snapshots`), keeping heartbeats and timers fresh without repeating every machine row, all in epoch milliseconds. Each build (`scripts/laundry/model.mts`) folds every whole day since the last into what it has learned (`src/laundry/model.mts`, on the same fold as the bus model), reading the day's rows from `/api/rows/:name` and storing the result with `/api/models/laundry`, and writes `src/laundry/usual.json`: for every room, kind, and hour of the week, the time-weighted free count and chance of any free, decayed with a 4-week half-life, leaving out stretches nobody watched and days a room was nearly idle, like breaks. The page reads each hour leaning on the room's all-hours average until that hour has been watched six hours, decayed, which held out did as well as the average alone and far better than the hours alone. Without `BUILD_TOKEN` or the Worker it keeps what it has, so it never fails the build.

## Deploying

Cloudflare Workers Builds builds and deploys the `notunh` Worker from this repo's `main` (Cloudflare dashboard, Worker → Settings → Build), on every push:

- Build command: `npm run build`, which in a fresh clone downloads the day's data, typechecks and tests, and only then learns the models, which writes D1, before building (`scripts/data.mts`). A preview build, of any branch but `main`, bundles the models as stored rather than learning, so it never changes what production learned. A build with `WORKERS_CI_BRANCH` unset and without `NOTUNH_OFFLINE`, as `npm run build` by hand, counts as `main`'s: it learns and writes production's models
- Deploy command: `npm run deploy`. Its `predeploy` script applies D1 migrations first; a migration failure stops deployment. Keep migration and deployment steps in `package.json`, so future changes don't require editing the dashboard command.

So each push runs in this order: build (fetch, typecheck and test, learn through the Worker deployed *before* this push, then Vite), migrate D1, then deploy the Worker and site together. Learning always talks to the previous Worker, so a change to the model API has to work against both: the first build of model revisions (migration 0002) meets a Worker whose `GET /api/models/:name` has no `revision`, and only reads, bundling the stored model if it's of its shape (else an empty one, as a new shape's first build would); migration 0002 then adds the revisions, the deploy brings the API that uses them, and the next build, by push or the nightly hook, learns. Deploying by hand, run the same three in the same order: `npm run build`, then `npm run deploy`.

**Rolling back.** Pages and the worker never go back to a copy published before the one they have, so a platform rollback (`wrangler rollback`, or a previous version in the dashboard) serves an older release that new visitors get but every installed client ignores until the next deploy; it's for emergencies, and Workers versions don't roll D1 back either, so the Worker it restores has to work with the current schema. To go back for everyone, publish the earlier release again: build it (a build of its commit is newer by construction, with today's data), or take the folder a build of it wrote and stamp it published now with `node scripts/republish.mts <folder>`, which keeps its code and data exactly, then deploy that folder (`wrangler deploy --assets <folder>`, after `npm run db:migrate`). Clients take it in over what's newer and reload into it out of view, and an edge still serving the release rolled back from is left alone. Only a build that reads the published stamp (2026-10-19 on) can be republished this way.

If upstream is down the build fails and the last deploy stays up. Cloudflare preview builds remain enabled. **Check** (GitHub Actions) also typechecks, tests, and builds each pull request without secrets and offline (`NOTUNH_OFFLINE=1`): its data is the fixtures under `tests/fixtures/data/`, so no pull request asks anything of upstream or the laundry vendor.

The Worker (`worker/`) is a small [Hono](https://hono.dev) app that only answers `/api/*` and the laundry rooms' addresses (`run_worker_first` in `wrangler.jsonc`); every other page and asset is served without it. Its cron triggers keep raw samples of the live API in the D1 database `notunh`, one gzipped row per source for every minute it polled, even when it saw nothing (`src/map/raw.mts`, each row naming the version of the normalization it was packed by, and from version 2 every poll it made, failed ones too, and the poll that first saw each fix): the buses' fixes polled six times a minute, and Umo's predictions every 5 minutes; and the laundry collector's changes. The samples are the source of truth, which visits and models are readings of: the **Observations** workflow (`.github/workflows/archive.yml`) archives each settled service day losslessly as the immutable release `observations-<day>` and lists it in `catalog.json` on the `observations` release (`src/map/archive.mts`), and `observationsOf(day)` in `scripts/observations.mts` reads a day from there or from D1 alike. Its tables are in `worker/schema.mts` (Drizzle), with migrations generated from it. Nightly at 4:17 AM (3:17 in winter, as cron runs in UTC) it prunes samples of days the catalog lists past `RETAIN_ARCHIVED_DAYS` (14), and any samples, laundry transitions, and polls past `RETAIN_DAYS` (60), extracted visits past `RETAIN_VISIT_DAYS` (180), daily model summaries past `RETAIN_SUMMARY_DAYS` (400), and laundry's records of rooms no longer listed and machines gone from their room, starts the Observations workflow, and on Mondays Map data, if it has a GitHub token for them (secret `GITHUB_TOKEN`, with the `actions` scope), and POSTs the Deploy Hook (Worker secret `DEPLOY_HOOK`), so Cloudflare rebuilds with fresh menus, timetable, and models.

The API, in `worker/api.mts`:

- `GET /api/health`, public: when each table's rows start and when the last was stored, in its own unit, and the day each model runs through
- `GET /api/rows/:name?day=YYYY-MM-DD&after=…` and `POST /api/rows/:name` (`{ rows, clear? }`): a page of rows from one table in the registry (`worker/rows.mts`: `buses`, `predictions`, `visits`, `transitions`, `polls`, `machines`), by Durham day or service day where the table has one, and writing the tables the build writes
- `GET /api/models/:name[?through=YYYY-MM-DD]` and `POST /api/models/:name` (`{ expect, state }`): the latest stored state of `buses`, `laundry`, or the `gtfs` feed by version, or the latest through a day, with its revision and every day the name is stored through; and a new one, stored only if the latest is still the revision `expect` says (or `null` for none), else 409
- `GET /api/storage`: how big D1 is, in bytes and rows a table; it counts every row, so only on demand
- `GET /api/laundry/rooms` and `GET /api/laundry/rooms/:id`, public, as in Laundry

The rows, models, and storage routes take `Authorization: Bearer $BUILD_TOKEN`, a Worker secret also set as a build variable, and answer 401 without it. Build steps reach them through `scripts/worker.mts`, which can also be run to look: `BUILD_TOKEN=… node scripts/worker.mts health`, `storage`, or `rows <name> [day]`, with `--local` for `npm run worker`.

**Refresh** (GitHub Actions) POSTs the same hook on demand, with `gh workflow run refresh.yml` (repository secret `CLOUDFLARE_DEPLOY_HOOK`).

**Observations** (GitHub Actions) archives the samples every night at 9:30 UTC, when the Worker dispatches it, or with `gh workflow run archive.yml -f from=<day> -f to=<day>` to backfill a range D1 still holds: for each settled service day of the last week not yet published, `scripts/archive.mts` reads its rows through `/api/rows/` (repository secret `BUILD_TOKEN`, the Worker's), stages them as `observations-<day>.ndjson.gz` with a `manifest.json` of its hash and counts, publishes them as the immutable release `observations-<day>`, the manifest last, and then merges every manifest into `catalog.json` on the `observations` release (creating that the first time), which the Worker's prune reads.

**Map data** (GitHub Actions) makes the map's OpenStreetMap data every Monday, when the Worker dispatches it, or with `gh workflow run map.yml`: it downloads the extract and Planetiler (caching Planetiler's 1.5 GB of water and Natural Earth data), runs `scripts/map/osm.mts`, which makes nothing if the generation is the one already published, checks the laundry and dining buildings still match, publishes the archive and its manifest as the release `map-data-<version>`, then moves `latest.json` on the `map-data` release to it (creating that the first time), and POSTs the same hook, if set, so the site rebuilds with it. Until it has first run, builds use the fixtures' walk and gazetteer and OpenFreeMap's tiles alone. A build fails rather than falling back on anything but a 404 of `latest.json`.
