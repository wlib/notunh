# notunh

The better UNH app, at [notunh.app](https://notunh.app): a PWA built with Vite and [bruh](https://github.com/Technical-Source/bruh), served as static assets from Cloudflare Workers.

Each section is its own page and bundle, sharing a shell (`src/shell/`: the `<head>`, theme, icons, Intl formatting, the one clock and visibility every page follows, remembered state, polling, and the service worker):

- `/` (`index.html.tsx`): what's here, who made it, and where the data comes from
- `/map/` (`map/index.html.tsx`, `src/map/`): live Wildcat Transit buses and routes on MapLibre GL with the OpenFreeMap Liberty style, and bus + walking directions
- `/dining/` (`dining/index.html.tsx`, `src/dining/`): dining hall menus, with search by food or ingredient and diet and allergen filters
- `/laundry/` (`laundry/index.html.tsx`, `src/laundry/`): which washers and dryers are free in every laundry room, and when each room is usually busy, with each room at its own address, like `/laundry/adams-tower/`

Within a section, `state.mts` holds the reactive state and live data, `ui/` the components, and the rest the logic, with the pure parts property tested. Each npm package builds into its own chunk, so a change to the app leaves maplibre cached.

### Offline first, updated live

Once built, every page opens from the cache at once, its code and data too, and the service worker (`src/sw/`, built to `/sw.js`) checks the network behind it:

- **A page's `<head>` is its release manifest** (`src/shell/manifest.mts`): when it was built (`<meta name="release">`), its code, including maplibre's worker, which `vite.config.mts` names there since only the code that starts it knows its name, and a preload link for each bundled JSON file, by name: the map's timetable, model, walking network, gazetteer, tiles week, style, and laundry and dining buildings, the dining index, and the laundry rooms' usual weeks. The build hashes them like code, so a page's HTML says exactly which code and which data it is, and they load alongside the code. Pages read their data through `latest(name, schema)` (`src/shell/build.mts`), a reactive value that everything derived from it follows; a file that doesn't fit its schema, which checks its shape and where it came from but takes big arrays of our own making on trust, is a load that failed like any other.
- **A newer copy of a page** is kept only once everything it names is in the cache, so it always opens whole offline, then sent to the page's open windows. If only its data differs, the page loads every changed file, swaps them in together where it is, keeping the trip, the itinerary chosen, the stop selected, and the map's camera, and tries again, later each time, for any that fails; a newer week of tiles is fetched afresh in place of the old, and a newer style comes in as the differences from the one showing. If its code differs, which a running page can't swap, the page reloads the next time it's out of view and not in the middle of a bus ride, or at once if it already is, so no one sees it, and picks up what it keeps between visits, like the trip being planned and the bus being ridden. No prompts. A page asks for its own copy to be checked when it comes back into view and every quarter hour in view, so a window that never navigates still hears of the nightly build; a copy from an older release than the one kept, as from an edge not yet caught up, is left alone.
- **Retention**: what the cache keeps is the closure of every generation still in use, which is each cached page's current and previous copy and whatever the open windows answer that they run, asked over a `MessageChannel` with a second to answer, and nothing else. A data file can ask for more than itself through one shape, `Retain = { files?, folders? }`: the dining index names its files, and the tiles and style manifests their folders, so the worker knows nothing of any of them. Pruning happens after a newer page is kept, on activation, and when the origin's quota is hit, where failing to keep a file never fails serving it: the worker prunes, then lets go of all the tiles, then all the fonts and sprites, once per storm.
- **Live data**, Umo's buses and the laundry API, is never cached, and each page polls it as before.

`tests/shell/sw.test.mts` drives the worker against an in-memory world, with the sequences from the 2026-10-18 reviews as named regressions, and `sw.model.test.mts` runs it against a model over generated sequences of releases, windows, going offline, a full quota, restarts, and frozen windows. `npm run test:browser` runs the same release sequences through Chromium and WebKit (`tests/browser/`), apart from `npm test`. [docs/storage.md](docs/storage.md) is the policy for every artifact and table: who makes it, its version, where it lives, how long, and how it goes.

Safari deletes a site's caches, service worker, and localStorage after seven days of use without a visit to it, unless it's on the home screen, and pages then come from the network as on a first visit, and are cached again.

The layers, each importing only those before it: `src/shared/` and `src/geo/`, which import nothing of ours; the walking network and the timetable (`src/map/graph.mts`, `feed.mts`, `shapes.mts`) on `geo`; routing (`walks.mts`, `plan.mts`) on those; publication and storage (`src/shell/`, `src/sw/`, the Worker, and `scripts/`) on `shared`; and the pages' state and UI on everything. `scripts/` import `src/`, never the other way, and `worker/` imports only `src/shared/`, `src/laundry/`, and the map's pure parts. `src/shared/` is what the pages, the Worker, and the build all use, with neither the DOM nor Node: Durham's clock and calendar (`time.mts`), the fold every learned model shares (`learn.mts`), `getJson`, which checks what it fetches against any Standard Schema it's given, and the slugs links name places by. Every boundary checks what crosses it with a [Valibot](https://valibot.dev) schema, which is also where its type comes from: Umo's, LaundryConnect's, Nutrislice's, and Photon's answers, keeping only the vehicles, predictions, machines, and places that fit, the data files the pages load, the map data release's pointer and manifest, and the bodies the Worker's build routes take, validated by `@hono/standard-validator` against `drizzle-valibot`'s schemas of the tables. `src/geo/` is the one geometry everything measures by, pure and knowing nothing of stops or the map: positions as `[lon, lat]` or `{ lat, lon }`, meters on the WGS84 ellipsoid by cheap-ruler's rulers (`projection.mts`, the only place one is made), lines measured out in meters with points and stretches along them, each with a ruler of its own for what's beside it (`lines.mts`), boxes always as west, south, east, north, indexed by Flatbush for finding what's near, and outlines as rings (`boxes.mts`), and map matching along lines (`follow.mts`). The transit side (`src/map/shapes.mts`, routes' shapes with their stops along them) and the walking network build on it, and so do the scripts. Time comes in two units, and only two:

- **Epoch milliseconds**, as `Date.now()` gives them, for every instant that crosses a boundary: Worker rows, API JSON, page state, and everything in laundry.
- **Schedule seconds** where times are compared with the GTFS timetable, which counts seconds from a service day's start: the planner, the bus model, and the visits it learns from, in the D1 `visits` table too.

A calendar day is a `Day`, `YYYY-MM-DD` in Durham, which sorts and compares as text, and weekdays count from Monday.

## Map

### Data

- **Live**: the Umo IQ rider API (`api.prd-1.iq.live.umoiq.com/v2.0/riders/agencies/unh`), the backend of `rider.umoiq.com` and the Umo apps. No key, open CORS, so browsers poll it directly: vehicles every 5 s, and predictions every 30 s for routes with a bus out.
- **Schedule**: Wildcat Transit's GTFS feed on National RTAP (the one Google Maps uses). The host has no CORS, so `npm run data` converts it into `src/map/gtfs.json` at build time, and CI rebuilds nightly. Umo's trip and stop ids match the GTFS ones, so predictions shift the timetable per trip. The first build to see a new feed version archives it in the Worker (`/api/models/gtfs`, as of that day), so a day's visits are always replayed against the timetable then in force.
- **OpenStreetMap**: Geofabrik's extract of New Hampshire, which the **Map data** workflow (`.github/workflows/map.yml`) downloads each week and `scripts/map/osm.mts` makes into everything the map has of OpenStreetMap: the streets and paths people walk around Durham, as the network in `src/map/walk.json`, the gazetteer in `src/map/gazetteer.json`, every place OSM names, with each one's kind, middle, and extent, and each building's outline and doors, and our own tiles (below). The three are one generation, each marked with where it came from (`src/map/made.mts`: the extract's date, and a hash of the code, campus profile, and Planetiler that made it, which together name the version), published whole as the immutable release `map-data-<version>`, one archive with a manifest of hashes, and then named by `latest.json` on the `map-data` release, so every build gets all of a generation or fails (`scripts/map/release.mts`). It reads the extract itself in about 3 s (`scripts/map/pbf.mts`: the file's framing, blocks, and protobuf are `@osmix/pbf`'s, and what OpenStreetMap's fields mean and how elements are gathered are ours, so a file cut short is refused as truncated rather than misread). While there's no release, the walk and gazetteer are the fixtures' (`tests/fixtures/data/src/map/`), which carry their provenance too; `npm run osm:refresh` takes the latest from the release, and `node scripts/map/osm.mts <extract.osm.pbf> <planetiler.jar> [--release <folder>]` makes them from an extract, the tiles too with Planetiler (and Java 21 or later), and stages the release.
- **Tiles**: made from the same extract with [Planetiler](https://github.com/onthegomap/planetiler) (`scripts/map/tiles.mts`) in two sets (`src/map/tiles.mts`), served from `public/data/map/tiles/<version>/<set>/{z}/{x}/{y}.pbf`: the OpenMapTiles base map Liberty draws, at zooms 10 to 14 around Durham, Dover, and Portsmouth, and a campus set in a schema of our own (`scripts/map/campus.yml`), at zooms 14 to 16 around Durham, with building names, parking lots, doors, benches, emergency phones, drinking water, fences and walls, and trees. Each set is cut to exactly the tiles wholly inside its boxes, which stay in New Hampshire, as the extract has nothing of Maine across the river, with an empty file where Planetiler made none, so every tile the map asks here for is here. The style names tiles as `tiles://<set>/{z}/{x}/{y}`, and the map's `tiles` protocol fetches each from here where the set has it, else from upstream (OpenFreeMap's pinned planet build, for the base map), else none, so a tile is wholly ours or wholly OpenFreeMap's and the two meet without a seam. They're stored uncompressed, as gzip only saves a quarter of them and maplibre can't read it without a `Content-Encoding` header; Cloudflare compresses them on the way if it takes their type to be compressible. About 1,200 files and 3.2 MB a version, and a build keeps the version the site served before beside the new one, so a tab still on last night's map isn't left without, against the free plan's 20,000 files per deploy.
- **Base map**: OpenFreeMap's Liberty style, which `scripts/map/style.mts` makes ours at build time (`src/map/style.mts`) in a folder under `public/data/map/` named by a hash of everything in it, so its style, sprite, and fonts always match, and names in `src/map/style.json`, which the map's page bundles like its other data: its sprite and the Latin and punctuation glyph ranges of its fonts served from our origin (rarer ranges still come from OpenFreeMap), its tiles ours where we have them and else from the planet build current then, so their URLs never change, our campus tiles drawn too, and its layers redrawn where they hide what's in the tiles: house numbers, bicycle parking and ATMs, woods, railways and platforms, campus land use and pitches, without unnamed flowerbeds, barriers, or bus stops our own stops already show. The service worker keeps the style's folder and the tiles' week with the page that names them, and lets them go with it.
- **Walking**: along the network (`src/map/graph.mts`, `src/map/walks.mts`), which keeps every part of OpenStreetMap's paths with twenty or more of them, to and from a building's nearest door where the gazetteer knows its doors, else from the place itself, joining the network by the nearest few paths and letting the shortest way decide. Where the network doesn't join a walk's ends, the walk is an estimate, a straight line a quarter longer, which the map draws dashed and faint rather than dotted.
- **Place search and names**: the gazetteer, stops, and laundry and dining buildings first, searched with uFuzzy as the dining page searches foods (`src/map/search.mts`), each name once, as the place by it nearest the middle of campus; Photon only for addresses, or when little is found here. A tapped spot is named by the map's label there, else the gazetteer's building it's in, by its outline where the gazetteer has it, or a place within 60 m, else the tiles' house number, else Photon (`src/map/gazetteer.mts`).
- **Laundry and dining buildings**: `scripts/map/places.mts` matches them to the campus's buildings in the gazetteer, into `src/map/places.json`. The laundry vendor puts every room at the same spot, so rooms are matched to their residence halls by name, with a small alias table where OSM names a building otherwise; a room or hall left unmatched fails the build. The map shows them quietly and plans to one when it's tapped, and `/map/?to=laundry/<room>` or `?to=dining/<hall>`, as the laundry and dining pages link, plans there from your location.

Buses are drawn where they likely are now, not just where they last reported: each one drives along its route and waits at each stop as long as the model expects at this time of day, scaled by how slow or quick buses on that line have been in the last half hour, nudged toward what the last bus took on that very stretch, and held at stops where its trip waits for the timetable.

Trip planning is a Connection Scan over the timetable plus live delays, with a reverse scan so each option leaves as late as possible. The timetable keeps each stop time's own word on getting on and off ("Arrivals Only" stops) and on getting there before leaving, and the planner never boards, alights, or arrives against it. Within the stretch Umo is predicting a route, trips it doesn't mention are dropped (the campus connectors run by headway, not to the timetable), and predictions older than three polls are dropped too, for the schedule. How early to be at a stop weighs the chance the bus waits there for its scheduled time, as the model has learned it, against how early it might otherwise leave, so a bus that waits half the time gets most of the slack of one that never does. Itineraries are kept across replans only while they would show the same, so a newer timetable's or fresher delays always come through, and the one chosen is remembered by its key.

### The model

Each build fits `src/map/model.json` (`scripts/map/model.mts`), bundled like the timetable. For every completed service day since the last model, it extracts each bus's visits to stops from the Worker's samples (`src/map/events.mts`, with the same snapping and zone crossing the map uses), stores them back in D1 as `visits`, which outlast the samples, and folds them into decayed statistics with a 4-week half-life (`src/map/model.mts`, on the fold in `src/shared/learn.mts`): drive times between stops by weekday or weekend and time of day, time at each stop, whether early buses wait at a stop for their scheduled time, layovers between trips, and how far off the timetable each route runs. Every estimate leans on a broader one while it has little data (a stretch at any time, then the route's pace), and an empty model has none, so the map falls back on its old constants. Each day is also scored (`scripts/map/replay.mts`): at 1, 3, 5, 10, and 20 minutes before each departure, how far off the timetable, the model from where the bus was, and Umo's own prediction were, which calibrates how much slack the planner leaves. The planner learns holds, layovers, and slack from it; Umo's predictions still set the delays.

Everything goes through the Worker's token-gated `/api/rows/:name` and `/api/models/:name` (see Deploying), so the build needs only `BUILD_TOKEN`, never D1 credentials, and learning runs only after the typecheck and tests pass. A model is stored only over the one the build read (a compare-and-swap on its last day), so two builds learning at once converge on one, the second bundling the first's rather than overwriting it. Without the token, or the Worker, the last model stays (or an empty one), so the model never fails the build. `npm run model -- --rebuild` refits from every stored visit, extracting again where samples are still kept, each day against the timetable archived for it.

## Dining

Menus come from Nutrislice (`unh.api.nutrislice.com`, behind `unh.nutrislice.com`): a week per hall and meal, with stations, ingredients, diet and allergen tags, and nutrition, published about two weeks ahead. It has no CORS, so `npm run data` fetches today through the end of what's posted, and splits it so the page only loads what it shows:

- `src/dining/menus.json`, the index the page bundles: halls, which meals each hall serves each day, and the name of every other file
- under `public/data/dining/`, each named by a hash of what's in it:
  - a file per hall per day, with each food's name, tags, and calories (about 2 KB gzipped)
  - a file per food, with its ingredients and nutrition, loaded when it's opened; a food served all week is one file, and stays cached across nightly rebuilds
  - every upcoming food with its ingredients and servings, loaded on the first search

The index names every file it uses, by path, and the service worker keeps them with it, dropping the rest once no retained index or open dining tab names them. Last night's files that tonight's index doesn't name stay published one more night (fetched back from the site, as a build starts from nothing), for tabs still on last night's. Search, filters, and everything else run in the browser.

## Laundry

The rooms' Speed Queen machines report to LaundryConnect (`laundryconnectlive.com`), which has no CORS, so the page asks the Worker. The room list reads `/api/laundry/rooms`, every room's free washers and dryers as the collector last saw them, made from D1 alone and shared at the edge for 5 minutes, so the list never reaches the vendor. An open room reads `/api/laundry/rooms/:id`, which fetches it live with the asker's own User-Agent and shares the answer for 30 s, falling back to the collector's last record (marked stale) when the vendor can't answer. `npm run data` lists the rooms into `src/laundry/rooms.json`, each with the slug of its address.

Each room has its own address, `/laundry/<room>/`: the Worker answers it with the laundry page (any other `/laundry/…` is a 404), the page moves between rooms with `history.pushState`, the service worker keeps the one laundry page for every room offline, where the page says when there's no such room, and `vite.config.mts` does the same in development.

`src/laundry/infer.mts` decides what to claim about each machine: a running machine's countdown is its own while it keeps reporting, a quiet one past its end is probably done, and a finished one sits done until its door opens.

The Worker's laundry cron polls every room every 5 minutes (15 overnight), a quarter of the rooms each minute between the fifths, and writes status changes to D1 (`transitions`, `latest`, `polls`) plus one current snapshot per room (`room_snapshots`), keeping heartbeats and timers fresh without repeating every machine row, all in epoch milliseconds. Each build (`scripts/laundry/model.mts`) folds every whole day since the last into what it has learned (`src/laundry/model.mts`, on the same fold as the bus model), reading the day's rows from `/api/rows/:name` and storing the result with `/api/models/laundry`, and writes `src/laundry/usual.json`: for every room, kind, and hour of the week, the time-weighted free count and chance of any free, decayed with a 4-week half-life, leaving out stretches nobody watched and days a room was nearly idle, like breaks. Without `BUILD_TOKEN` or the Worker it keeps what it has, so it never fails the build.

## Commands

```sh
npm run dev        # http://localhost:5173, fetching data first if it's missing
npm run data       # refresh every data file from upstream, and the models from the Worker (`-- fetch` or `-- learn` for one stage)
npm run fixtures   # remake tests/fixtures/data from the data fetched, for offline builds and the walk and gazetteer fallbacks
npm run icons      # regenerate app PNG icons from public/icon.svg
npm test           # property tests (vitest + fast-check)
npm run test:browser  # the service worker through real browsers (Playwright; once: npx playwright install chromium webkit)
npm run typecheck
npm run worker     # the Worker on http://localhost:8787 with a local D1, crons fired by
                   # curl "localhost:8787/cdn-cgi/handler/scheduled?cron=*+*+*+*+*"
npm run model -- --local  # fit the bus model from it, with BUILD_TOKEN set here and in .dev.vars
npm run storage    # how big D1 is, in bytes and rows a table (BUILD_TOKEN=…)
npm run db:generate       # a migration in worker/migrations for changes to worker/schema.mts
npm run db:migrate # apply production D1 migrations
npm run deploy     # migrations, then deploy the existing build
npm run deploy:fresh # fresh data, build, then deploy with migrations
```

## Deploying

Cloudflare Workers Builds builds and deploys the `notunh` Worker from this repo's `main` (Cloudflare dashboard, Worker → Settings → Build), on every push:

- Build command: `npm run build`, which in a fresh clone downloads the day's data, typechecks and tests, and only then learns the models, which writes D1, before building (`scripts/data.mts`)
- Deploy command: `npm run deploy`. Its `predeploy` script applies D1 migrations first; a migration failure stops deployment. Keep migration and deployment steps in `package.json`, so future changes don't require editing the dashboard command.

If upstream is down the build fails and the last deploy stays up. Cloudflare preview builds remain enabled. **Check** (GitHub Actions) also typechecks, tests, and builds each pull request without secrets and offline (`NOTUNH_OFFLINE=1`): its data is the fixtures under `tests/fixtures/data/`, so no pull request asks anything of upstream or the laundry vendor.

The Worker (`worker/`) is a small [Hono](https://hono.dev) app that only answers `/api/*` and the laundry rooms' addresses (`run_worker_first` in `wrangler.jsonc`); every other page and asset is served without it. Its cron triggers keep raw samples of the live API in the D1 database `notunh`, one gzipped row per source per minute (`src/map/raw.mts`): the buses' fixes polled six times a minute, and Umo's predictions every 5 minutes; and the laundry collector's changes. Its tables are in `worker/schema.mts` (Drizzle), with migrations generated from it. Nightly at 4:17 AM (3:17 in winter, as cron runs in UTC) it prunes samples, laundry transitions, and polls past `RETAIN_DAYS` (60), extracted visits past `RETAIN_VISIT_DAYS` (180), and laundry's records of rooms no longer listed and machines gone from their room, starts the Map data workflow on Mondays if it has a GitHub token for it (secret `GITHUB_TOKEN`, with the `actions` scope), and POSTs the Deploy Hook (Worker secret `DEPLOY_HOOK`), so Cloudflare rebuilds with fresh menus, timetable, and models.

The API, in `worker/api.mts`:

- `GET /api/health`, public: when each table's rows start and when the last was stored, in its own unit, and the day each model runs through
- `GET /api/rows/:name?day=YYYY-MM-DD&after=…` and `POST /api/rows/:name` (`{ rows, clear? }`): a page of rows from one table in the registry (`worker/rows.mts`: `buses`, `predictions`, `visits`, `transitions`, `polls`, `machines`), by Durham day or service day where the table has one, and writing the tables the build writes
- `GET /api/models/:name[?through=YYYY-MM-DD]` and `POST /api/models/:name` (`{ expect, state }`): the latest stored state of `buses`, `laundry`, or the `gtfs` feed by version, or the latest through a day, with every day the name is stored through; and a new one, stored only if the latest is still through the day `expect` says (or `null` for none), else 409
- `GET /api/storage`: how big D1 is, in bytes and rows a table; it counts every row, so only on demand
- `GET /api/laundry/rooms` and `GET /api/laundry/rooms/:id`, public, as in Laundry

The rows, models, and storage routes take `Authorization: Bearer $BUILD_TOKEN`, a Worker secret also set as a build variable, and answer 401 without it. Build steps reach them through `scripts/worker.mts`, which can also be run to look: `BUILD_TOKEN=… node scripts/worker.mts health`, `storage`, or `rows <name> [day]`, with `--local` for `npm run worker`.

**Refresh** (GitHub Actions) POSTs the same hook on demand, with `gh workflow run refresh.yml` (repository secret `CLOUDFLARE_DEPLOY_HOOK`).

**Map data** (GitHub Actions) makes the map's OpenStreetMap data every Monday, when the Worker dispatches it, or with `gh workflow run map.yml`: it downloads the extract and Planetiler (caching Planetiler's 1.5 GB of water and Natural Earth data), runs `scripts/map/osm.mts`, which makes nothing if the generation is the one already published, checks the laundry and dining buildings still match, publishes the archive and its manifest as the release `map-data-<version>`, then moves `latest.json` on the `map-data` release to it (creating that the first time), and POSTs the same hook, if set, so the site rebuilds with it. Until it has first run, builds use the fixtures' walk and gazetteer and OpenFreeMap's tiles alone. A build fails rather than falling back on anything but a 404 of `latest.json`.
