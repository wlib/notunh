# Storage policy

Every artifact and table notunh makes: who makes it, when, what version it is, what it may be mixed with, where it lives, how long, and how it goes. The code named in each row is the source of truth; this is the map of it.

## Pipeline

A build (Cloudflare Workers Builds, from `main`, nightly from the Worker's cron and on push) runs `npm run build`, whose `prebuild` is, in order (`package.json`, `scripts/data.mts`):

1. **fetch**, read-only ingest: `scripts/map/gtfs.mts`, `map/style.mts`, `dining/menus.mts`, `laundry/rooms.mts`, `map/osm.mts`, `map/places.mts`
2. `npm run typecheck`, `npm test`
3. **learn**, which writes D1 through the Worker's API: `scripts/map/model.mts`, `scripts/laundry/model.mts`. It never fails the build: without `BUILD_TOKEN` or the Worker the last file stays, or an empty model. Only a build of `main` learns (Cloudflare's `WORKERS_CI_BRANCH`), as does a command run by hand; a preview build of any other branch bundles the models as stored, only reading (`scripts/learn.mts` `isLearning`), as does a build reaching a Worker from before model revisions, which the first build of them does, as it runs before its Worker deploys
4. `vite build`, then `npm run deploy`, whose `predeploy` applies D1 migrations

`npm run dev` runs fetch alone, so a checkout never learns. Pull requests (`check.yml`) build with `NOTUNH_OFFLINE=1`: fetch copies `tests/fixtures/data/` in, learn does nothing, and no pull request reaches the GTFS host, Nutrislice, the laundry vendor, or GitHub releases. The fixtures are remade from a real build's data by `npm run fixtures` (`tests/fixtures/make.mts`), and are the fallbacks for the walk and gazetteer while there's no map data release.

## Browser caches and eviction

The service worker keeps one Cache Storage cache, and what it keeps is the **closure of every generation in use**: each cached page's current and previous copy, whatever open windows answer they run (a census over `MessageChannel`, a second to answer), and what each one's data asks for by the `Retain` shape (`src/shell/manifest.mts`): the style manifest its `required` `style.json`, fetched before the page is kept, the dining index its `files`, kept if present, the tiles and style manifests their `folders`. Nothing else. Pruning runs after a newer page is kept, on activation, and when the origin's quota is hit, always in turn with the cache's writes on one queue. A release is kept only once every file of it is confirmed kept and is what its name says (`isKeepable`: a `.js`, `.css`, or `.json` must answer as one, and nothing hashed may answer as a page); an ordinary request is answered whether or not its response can be kept. The cache is named anew (`app-v2`) when what it keeps changes meaning, and activating deletes every older one. The first worker's (`app-v1`) pages named only their code, which loaded their data and maplibre's worker by URL, so what they need can't be told: they're fetched afresh like a page not visited yet, and a tab still open on one fetches what it hadn't loaded from the network. When one of its hashed files is gone (a 404, or no network and no copy), the worker sends that tab to its page afresh, once, since its code can't recover by itself; a page that answers the census retries its own files instead.

The eviction verdict (`notunh-eviction-2026-10-18.md`): **no LRU, LFU, or byte cap**. What a browser can store is bounded by what's published, as the worker keeps only pages, `/assets/`, `/data/`, and the icons: about 14 MB with each page's two generations, more only while open windows still run older ones, against a 1 GiB floor quota, so a frequency policy would never act and would cost a write per hit. On `QuotaExceededError`, `store` never fails the response: it climbs the ladder, prune, then all the tiles, then the style's fonts and sprites, each rung once per storm, which lasts until a put succeeds or a page is next taken in: puts failing together await the same rung's surrender rather than each climbing one, and otherwise it answers from the network uncached (`src/sw/worker.mts` `SURRENDERABLE`). Pages, what they name, and the style JSON are never surrendered.

The HTTP cache sits behind the worker: pages are fetched with `cache: "no-cache"`, so a page's HTML is always the edge's; hashed assets are immutable by name and may be served from the HTTP cache on a first fill.

### iOS and Safari

- **Seven-day rule**: Safari deletes all of a site's script-writable storage, the cache, the service worker, and `localStorage`, after seven days of Safari use without interacting with the site. A home-screen app is exempt. Pages then come from the network as on a first visit and are cached again; the remembered state is gone, which the pages treat as a first visit.
- **Quota**: iOS 16.4 (our floor) gives an origin about 1 GiB; Safari 17+ about 60 % of disk, and 15 % in other apps' web views. Exceeding the origin's quota throws `QuotaExceededError`, which the ladder handles; exceeding the overall quota evicts whole origins, least recently used first, which nothing here can prevent and the first visit handles.
- Old deployed tabs: a tab on last night's page may ask for files the origin no longer has. The origin keeps the generation before the current one everywhere for this, as the browser keeps each page's previous copy: the tiles' folder and the style's folder one build, and the dining children one build and 48 h past the last index naming them. A tab older than that, which the browser covers only while it answers the census, 404s on an uncached file (maplibre draws without a glyph range or sprite) until it reloads, which it does once out of view with a newer build announced, or at once after an hour away.

## Worker and D1

D1's free plan allows 500 MB per database and 5 M rows read a day. Measured on October 7 to 19 (`notunh-model-research/2026-10-19_location/harness/size.mts`), a weekday is about 30 k bus fixes in about 1,150 minute rows, 620 KB of gzipped bodies in D1 besides row overhead, and predictions about 280 KB; weekends about a third of that. So samples are about 1 MB a weekday in D1, 14 MB at the two weeks kept once archived, and at most about 60 MB at the 60-day cap while the archive is failing. The same day as one ndjson file is 2.1 MB raw, 400 KB with gzip -9 (brotli 11 is 310 KB, zstd 19 325 KB, but gzip reads everywhere: `zcat`, Node, and browsers' `DecompressionStream`), and predictions 190 KB, so the archive grows about 0.6 MB a weekday, 200 MB a year, on GitHub. Two weeks in D1 covers a fortnight of failed builds or refits reading recent days without GitHub, and the archive workflow's week of looking back twice over; the 60-day cap is the fallback whenever the catalog can't be read or doesn't list a day. A day's model summary is about 86 KB of JSON (24 KB gzipped), so 400 days of `summaries` are about 35 MB, long enough to set a week beside the same week a year before. Visits about 7 k rows a day, about 120 B each with the `umo` column (a sampled prediction at each of the model's 7 leads, 5 before 2026-10-19), which at 365 days would approach 300 MB, so `RETAIN_VISIT_DAYS` is 180: with the model's 28-day half-life a day 180 days back weighs 1 % of today's, and only `--rebuild` reads further back. The `umo` column stays because `--rebuild` rescores Umo's forecasts from stored visits (`replay.mts` `score`), which is the one record of how Umo did on a day.

Measure rather than estimate: `npm run storage` (`GET /api/storage`, token-gated) answers `{ bytes, rows: { table: n } }`, `bytes` from D1's own `size_after`. Counting reads every row, so it's on demand only; `GET /api/health` stays cheap (two index lookups a table) and public.

Models are stored with compare-and-swap on the latest row's `revision`, the latest being the last written (`written`), which every write renews: a build that reads model `M` and tries to store over anything written since gets a 409 and bundles the newer one instead (`scripts/learn.mts`), so two builds learning at once, or two replacing the same day, converge on one line of models rather than overwriting each other. Visits and summaries are replaced a day at a time with `clear`, each request transactional; a build cut off between the clear and its last page leaves a day short until the next build, which extracts it again from samples while they're kept.

## GitHub

The Map data workflow publishes a generation only when the pointer doesn't already name it (`osm.mts` compares versions before Planetiler runs), so the Monday schedule and the Worker's Monday dispatch (nightly cron, with `GITHUB_TOKEN`) can both fire without publishing twice. GitHub pauses the schedule after 60 days without a commit; the dispatch doesn't pause, but needs the secret. Without it, and without commits, map data stops refreshing after 60 days until `gh workflow run map.yml`.

The Observations workflow (`archive.yml`) publishes each settled service day not yet published, looking back a week, so a failed night is made up by the next, and a dispatch with `from` and `to` backfills any range D1 still holds. It reads the Worker with the repository secret `BUILD_TOKEN` (the Worker's own). A day's release is immutable once its `manifest.json` is up: a later run only merges that manifest into the catalog again, and a release left without one is filled in again from D1, which still has the day since the catalog never listed it. `catalog.json` is merged into, never rebuilt, and uploaded last, so the Worker never prunes a day whose archive isn't whole; a catalog that can't be downloaded fails the run rather than be replaced. Readers verify a day's file against its manifest's hash and size (`scripts/observations.mts`). Like Map data, its schedule pauses after 60 days without a commit, so the Worker's nightly run dispatches it every night given `GITHUB_TOKEN`; without either, samples stay their 60 days and are lost past them.

Releases are never deleted by anything here. Each is a few MB; deleting old `map-data-<version>` releases by hand is safe once no build names them, which is after the next build.
